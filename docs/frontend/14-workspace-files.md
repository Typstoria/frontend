# Керування файлами

Статус: наступний інкремент FE2b після текстового редактора й автозбереження. Доступні створення текстових файлів, зміна шляху, видалення та вибір головного файла. Контекст і ресурси завершують FE2b. PDF належить до FE3.

## Інтерфейс

У заголовку дерева меню «Додати файл» містить дію «Створити файл». Шлях може містити каталоги, наприклад `chapters/intro.typ`; окремих порожніх папок API не створює. Новий файл початково порожній, після підтвердження сервера відкривається в редакторі.

Меню активного файла у верхній панелі пропонує перейменування, видалення та, для текстового `.typ`, «Зробити головним». Перейменування змінює повний шлях і зберігає fileId, текст, cursor/undo. Зірочка праворуч позначає головний файл; вибір іншого файла в редакторі сам по собі не змінює головний.

Видалення має явне підтвердження. За наявності dirty тексту попереджає про його втрату. Видалення головного файла або перейменування його у шлях без case-sensitive `.typ` потребує вибору іншого текстового `.typ` у тому самому діалозі; обидві операції застосовуються разом. Якщо кандидатів немає, дія заблокована до створення іншого `.typ`. Історичні snapshot зберігаються в бекенді; frontend restore ще не реалізовано.

На mobile дія створення спершу закриває панель файлів, потім відкриває форму. Діалоги утримують фокус і повертають його після закриття. Submit і закриття блокуються до завершення всієї операції, включно із завантаженням вибраного файла після видалення.

## Шляхи та обмеження

Шлях нормалізується у NFC, без trim. Дозволено відносні POSIX-шляхи; відхиляються порожні сегменти, `.`, `..`, backslash, двокрапка, control characters, некоректний Unicode та службові `.git`/`.typstoria` без урахування регістру. До 255 байтів UTF-8 на сегмент і 1024 на весь шлях. Перевіряються нормалізовані дублікати та конфлікт file/directory.

Проєкт має до 500 файлів. Головний — наявний текстовий файл із закінченням `.typ`, з урахуванням регістру. Інші текстові файли не обмежуються цим розширенням. Ліміти тексту й atomic body описано в [13](13-workspace-autosave.md); backend остаточно перевіряє всі дані та квоти. Вміст Typst не компілюється під час цих дій.

## Запис, повтори та конфлікти

Структурна дія й dirty тексти надсилаються одним `POST /changes`. Незбережений текст файла, видалення якого користувач підтвердив, не додається як окреме оновлення перед видаленням. Паралельних save немає; пакет і ключ фіксуються до відправлення. Після невідомого результату текст файла, що очікує видалення, доступний для копіювання, але редагування заблоковано; інші тексти залишаються редагованими й зберігають новіші правки.

Success перевіряє `createdFiles` та ID/шляхи створених файлів і перечитує канонічний state **за прийнятою revisionId**, а не довільний поточний snapshot. Після read success оновлюються дерево, mainFileId і базові тексти; пізніші edits залишаються dirty. Втрата POST-відповіді вимагає того самого body/key. Якщо POST уже підтверджено, а наступний GET не вдався, `refresh_failed` утримує результат: «Оновити файли» повторює лише GET, не створюючи нового запису.

Відома відмова зберігає намір та повідомлення до явного повтору, виправлення форми або скасування. Введення тексту чи повторний вхід не повторюють відхилену структурну дію автоматично. Guard виходу враховує наміри та незавершені пакети, навіть якщо текст clean.

`409` утримує намір окремо від remote snapshot. Порівняння показує опис дії та checkbox повтору, початково вимкнений. Складена дія на кшталт delete+setEntrypoint повторюється лише як одна група. Перевіряється фінальне дерево відносно переглянутої remote версії; відсутній файл або колізія шляху блокують повтор цієї дії. Тексти узгоджуються окремо. Лише підтвердження вибору встановлює нову base revision і відновлює autosave.

Recovery у пам’яті тієї самої вкладки містить намір, фазу запиту, прийнятий результат і незавершене порівняння. Інший акаунт його не бачить. Backend idempotency обмежений сеансом: після нового входу невідомий попередній пакет може отримати stale-base conflict замість replay. UI обробляє це явним узгодженням; уже створений файл не створюється вдруге. Reload або закриття вкладки не зберігають локальну recovery. JSON-копія чернетки включає також наміри зміни файлів.

## Перевірки

Unit tests перевіряють Unicode/NFC/path boundaries, final-tree/main constraints, atomic text+structure, created mapping, immutable retry, refresh-only retry та recovery, grouped conflicts, failed recovery без auto replay й повторний submit під час replacement load. Playwright покриває основні дії, validation та негативні сценарії на desktop/mobile з підмінами API.

Окремий smoke зі справжнім API/PostgreSQL перевірив створення з реально загубленою POST-відповіддю й idempotent retry, rename зі сталим ID, main switch і delete+replacement у browser UI на desktop та mobile. Mobile сценарій також відкликав сеанс після невідомого create і перевірив повторний вхід, stale-base reconciliation та відсутність дубля створеного файла. Тимчасові дані прибрано.

## Контекст і ресурси

Кнопка «Контекст» відкриває окремий режим редактора. Текст контексту зберігається в тій самій чернетці та ревізії, що й файли. Конфлікт контексту показує початковий, серверний і локальний текст. Копія чернетки включає контекст.

Дія «Завантажити файл» у меню «Додати файл» відкриває вибір файла й шляху. Підтримуються зображення PNG, JPEG, GIF, WebP, PDF і шрифти TTF, OTF, WOFF та WOFF2. Розмір файла обмежено 10 МіБ. «Замінити файл» у меню файла зберігає шлях і ID та вимагає сумісного формату. «Скачати файл» читає ресурс із відкритої ревізії.

Під час вибору й завантаження ресурсу автозбереження чекає завершення діалогу. Після підтвердження завантаження одна операція збереження додає або замінює ресурс разом із чернеткою. Повтор після невідомого результату збереження використовує той самий пакет і ключ. При втраченій відповіді на завантаження повтор може створити ще один тимчасовий запис, строк дії якого становить 24 години. Конфлікт повторно застосовує ресурс лише після явного вибору, а зміна шляху чи вмісту цільового ресурсу в іншій вкладці вимагає перегляду перед заміною.
