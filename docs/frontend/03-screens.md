# Екрани та навігація

Статус: основна інформаційна архітектура v0.1. Остаточні візуальні рішення — за [дизайн-брифом](09-design-and-mockups.md).

## 1. Карта екранів

| Екран                     | Цільовий маршрут                             | Основні дії                                                                    |
| ------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------ |
| Вхід/реєстрація           | `/auth/login`, `/auth/register`              | Email/password, Google, verify/resend guidance                                 |
| Посилання з листів        | `/auth/verify-email`, `/auth/reset-password` | Явне підтвердження або новий пароль                                            |
| Відновлення               | `/auth/forgot-password`                      | Generic відповідь, cooldown                                                    |
| Проєкти                   | `/projects`                                  | Пошук, створення, шаблон, імпорт, rename/delete                                |
| Робочий простір           | `/projects/:projectId`                       | Файли, текст, PDF, контекст, структура, annotations                            |
| Пропозиція                | `/projects/:projectId/proposals/:proposalId` | Diff, validation, candidate PDF, accept/reject                                 |
| Історія                   | `/projects/:projectId/history`               | Read-only версія, diff, restore як нова версія                                 |
| Шаблони                   | `/templates`, `/templates/shared#…`          | Каталог у верхній навігації, обкладинки першої сторінки, копія й поширення     |
| Доступи й обліковий запис | `/settings/account`                          | OAuth-підключення та відкликання; ім’я, пошта, зміна пароля, видалення акаунта |
| Backup                    | `/projects/:projectId/settings/backup`       | GitHub repo/branch, склад копії, status/retry                                  |

OAuth consent route має визначити backend authorization flow; не вигадуємо робочий URL наперед. Експорт і upload progress можуть бути панелями, окрема сторінка для кожного job не потрібна.

Реалізовано всі п’ять основних auth-сторінок та `/auth/delete-account` для явного підтвердження видалення, захищені `/settings/account` і `/projects` зі списком, створенням, перейменуванням та видаленням, відкриті `/preview/workspace`, `/preview/review` та 404. Без сеансу приватні маршрути ведуть на вхід; повернення дозволене лише до відомих внутрішніх сторінок. Історія доступна в тому самому робочому просторі за `/projects/:projectId/history`. Інші маршрути таблиці — цільові. Preview routes містять лише статичні зразки, посилання на них показуються в навігації лише під час перегляду цих макетів. Назва проєкту відкриває захищений `/projects/:projectId` з наявними текстовими файлами, CodeMirror та автозбереженням; деталі — у [13](13-workspace-autosave.md). Деталі поточної сторінки — у [11-projects.md](11-projects.md).

## 2. Робочий простір

```text
Проєкти / Назва проєкту               Стан автозбереження   [Скомпілювати]
Файли / Структура | Вкладки файлів і Typst editor | PDF, ревізія, стан
                 |                               | page / zoom / download
                 | Діагностика з переходом        |
Контекст · Матеріали · Анотації · Пропозиції · Історія
```

Desktop: дерево, editor, PDF; користувач змінює ширину/ховає панелі. Нижня діагностична панель не перекриває текст. Контекстні матеріали відокремлені від дерева компіляції, щоб upload джерела інформації не виглядав як додавання ресурсу до PDF.

У поточному інкременті editor займає решту висоти вікна; на телефоні дерево файлів відкривається модальною бічною панеллю, закривається після вибору та повертає фокус перемикачу. PDF відкривається поряд із кодом від 1024 px. На вужчому екрані кнопка «Результат» перемикає редактор і PDF або діагностику. Команди save/compile та попередження про незбережені зміни залишаються доступними. Full desktop tooling на телефоні не є умовою першого інкременту, але читання, review і базове редагування мають бути можливі.

Вибір файла прив’язаний до сталого fileId. Rename змінює шлях, не створює нову логічну вкладку. Історична версія й candidate відкриваються read-only з явною назвою режиму.

## 3. Review

Заголовок: мета, автор/клієнт, base revision, candidate version і validation status. Ліворуч список **усіх** операцій: текст, binary metadata, rename/delete, context/materials/annotations. У центрі diff, праворуч або вкладкою candidate PDF/diagnostics. Кнопки рішення поруч із результатом перевірки.

Після зміни candidate попередній перегляд і підтвердження втрачають чинність. Stale показує зміну бази та дію повторної перевірки; автоматичного merge немає. Для compile failure окремий діалог із фактичними помилками та непозначеним acknowledgement.

## 4. Загальні стани

Кожний data screen має loading, empty, error/retry, denied/not-found та ready. Empty проєктів після успішного GET відрізняється від помилки завантаження. Демонстраційні дані не використовуються як fallback при помилці API.

Помилка містить зрозуміле пояснення та потрібну дію. Request/trace IDs, внутрішні коди й HTTP-статуси залишаються в API та діагностиці, не в користувацькому інтерфейсі. Toast підходить для допоміжного успіху; конфлікт, втрата доступу, compile error та незбережений текст потребують постійного видимого стану.

Компонент `LoadError` показує помилку завантаження як стан цілої сторінки або окремої секції. Екран передає заголовок, пояснення та доступні дії. Якщо проєкт недоступний, можна повернутися до списку. Якщо збій тимчасовий, можна повторити запит на місці.
