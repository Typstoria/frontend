# Черга змін редактора після ручної перевірки

Дата: 16 листопада 2026 року. Статус: робоча черга для послідовного обговорення. W01 і W02 реалізовано. У W03, W04, W06, W08 і W09 виконано окремі зміни інтерфейсу, зазначені нижче. Цей список фіксує побажання користувача; деталі кожного пункту узгоджуємо окремо перед реалізацією. Не переходити до наступного пункту без доручення.

Орієнтири: досвід IDE, перемикач режимів прев’ю на зразок Android Studio, вкладки, дерево та історія на зразок JetBrains. Усі елементи мають виконувати реальну дію; іконки отримують зрозумілі tooltip і доступні назви. Перевіряти desktop і mobile. Нові продуктові блоки поза переліченими тут не додаються.

## W01 — Останній успішний PDF при відкритті проєкту

- [x] Обговорити контракт, строк зберігання та початковий стан.
- [x] Реалізувати й перевірити.

Під час відкриття проєкту автоматично знаходити та показувати останній успішний PDF прийнятого документа. За наявності доступного PDF не вимагати нової компіляції лише для появи панелі. Якщо новіші зміни ще не скомпільовані або компіляція впала, залишати попередній успішний результат. PDF ШІ-пропозиції не підміняє прийнятий документ; старіша ревізія, скомпільована пізніше, не витісняє новішу.

Погоджено початкову поведінку: якщо доступного останнього PDF немає, автоматично запускати компіляцію поточної збереженої ревізії при відкритті проєкту. Це стосується як першої компіляції, так і відсутнього чи простроченого артефакту. Якщо задача для цієї ревізії вже queued/running, підключатися до неї без дублювання. Недоступність API не трактувати як підтверджену відсутність PDF. Початкове очікування показує стан завантаження; shimmer належить до W04. Помилка компіляції завершує спробу й показує діагностику, без нескінченних автоматичних повторів.

Реалізовано GET `/compilations/latest-pdf` та POST `/compilations/ensure`. Семиденний TTL PDF поки збережено: за відсутності доступного результату запускається або підхоплюється поточна збережена ревізія. Продовження строку зберігання останнього PDF не потрібне для цього сценарію й залишається окремим можливим рішенням. Обкладинка проєкту — окремий PNG зі своїм життєвим циклом.

Готово, коли reload і повторне відкриття показують доступний попередній PDF без зайвої компіляції; за підтвердженої відсутності PDF автоматично запускається або підхоплюється одна задача поточної збереженої ревізії. Помилка compile й недоступність API мають зрозумілі окремі стани.

## W02 — Зрозумілі режими робочого простору

- [x] Визначити режими, іконки й початкову розкладку.
- [x] Реалізувати й перевірити.

Перемикач іконками має режими «Лише код», «Код і PDF» та «Лише PDF». На широкому екрані початково відкриваються обидві панелі. На вузькому екрані початково відкривається код, доступні лише режим коду й режим PDF.

Рішення цього пункту задає структуру для PDF, нижньої діагностики та подальшого resize. Не додавати режими, які реально не працюють.

## W03 — PDF як документ із безперервною прокруткою

Іконки завантаження та відкриття PDF в іншій вкладці готові.

- [ ] Обговорити toolbar, масштабування й збереження позиції.
- [ ] Реалізувати й перевірити.

- Усі сторінки розташовані послідовно згори вниз; прибрати кнопки «Попередня/Наступна».
- Додати масштабування, кнопки збільшення/зменшення й режим під ширину. Погодити колесо з Ctrl/Cmd та pinch-жест на touch; звичайне колесо прокручує документ.
- Завантаження PDF — кнопка з іконкою. Окремо — іконка відкриття PDF у новій вкладці.
- При заміні PDF зберігати масштаб і позицію читання: сторінку та відносне місце на ній; якщо сторінок стало менше, вибирати найближчу доступну позицію.
- Новий результат підміняє старий після підготовки, без стрибка на початок і без проміжного порожнього екрана.
- Для великих PDF рендерити видимі й сусідні сторінки з обмеженням пам’яті, зберігши текстовий шар.

Відкриття нової вкладки має працювати з приватною Bearer-авторизацією: не передавати токен у URL. Вибір між окремим viewer route та Blob URL належить до технічного обговорення цього пункту.

## W04 — Очікування компіляції та діагностика

Готові спрощені статуси, відкладений shimmer і компактний індикатор оновлення зі збереженням видимого PDF.

- [ ] Обговорити shimmer й поведінку нижньої панелі.
- [ ] Реалізувати й перевірити.

Прибрати користувацькі статуси на кшталт «У черзі»: queued/running залишаються внутрішніми станами. Для початкового очікування показувати контур аркуша зі shimmer. Коли PDF уже є, залишати його читабельним; погодити ненав’язливий індикатор оновлення замість перекриття всього документа. Анімація враховує reduced motion.

Винести помилки й попередження компіляції в нижню панель, окремо від PDF. За появи помилки панель відкривається; її можна закрити й відкрити знову, а клік по повідомленню веде до відповідного файла. Погодити поведінку після успішного виправлення. Повідомлення про помилки збереження й конфлікти не маскувати індикатором компіляції.

Зараз backend повертає для діагностики файл, але не точну позицію. Точний перехід до рядка потребує серверної підтримки; поточний файл можна відкривати одразу.

## W05 — Постійна автокомпіляція після автозбереження

- [ ] Обговорити затримки, чергу та обробку помилок.
- [ ] Реалізувати й перевірити.

Автокомпіляція працює постійно, без перемикача налаштування. Після успішного збереження змінених вхідних файлів автоматично оновлювати PDF. Лише зміна контексту або стану інтерфейсу не потребує компіляції. Прибрати вимогу вручну «зберегти й скомпілювати» та підказку повторно скомпілювати для звичайного редагування. Погодити, чи лишається іконка примусового повтору для збою або повторної спроби.

Не створювати compile job на кожне натискання клавіші. Згортати серію правок до актуального збереженого стану: якщо під час роботи з’явилися нові зміни, після неї запускати потрібний найновіший стан. Не допускати накопичення застарілої черги, нескінченних повторів синтаксичної помилки чи витіснення новішого PDF пізнім результатом. Непідтверджене збереження, конфлікт і завершення сеансу мають окрему визначену поведінку.

Залежить від W01–W04: старий PDF залишається видимим, новий оновлює його без втрати масштабу та прокрутки, а помилки з’являються знизу.

## W06 — Історія у широкому діалозі

Поточну версію можна вибрати й переглянути. Посилання повернення називається «Повернутися до редактора».

- [ ] Обговорити структуру діалогу та перегляд поточної версії.
- [ ] Реалізувати й перевірити.

Відкривати історію поверх поточного workspace у широкому діалозі; на mobile можна займати весь екран. Зберегти список версій, дерево файлів вибраної версії, текст, diff та відновлення. Дати очевидне закриття, Escape і повернення фокуса. Після закриття редактор, вкладки й PDF залишаються в попередньому стані. Якщо `/history` лишається як deep link, він теж відкриває діалог поверх редактора й має зрозуміле закриття.

Поточна версія має бути доступна для вибору й перегляду. Позначка поточної версії пояснює її стан; недоречне відновлення тієї самої версії не робить весь рядок неактивним. Погодити базу порівняння. Відновлення як і зараз створює нову ревізію, потребує підтвердження та не втрачає незбережені правки.

## W07 — Вкладки файлів і контексту

- [ ] Обговорити модель вкладок, їх відновлення та місце відкриття контексту.
- [ ] Реалізувати й перевірити.

Відкриті файли отримують вкладки зі стабільною прив’язкою до file ID. Контекст відкривається як окрема вкладка в тій самій смузі, з явною назвою та закриттям. Повторна дія акцентує вже відкриту вкладку, замість toggle, який змінює значення кнопки. Контекст залишається окремими даними проєкту, не створює фізичного файла в дереві та не компілюється.

Потрібні закриття вкладки, зміна порядку перетягуванням і контекстне меню: закрити поточну, інші, усі та вкладки праворуч. Погодити поведінку середньої кнопки миші й клавіатурні дії. Cursor, undo й scroll файлів не губляться при перемиканні та перейменуванні. Закриття вкладки саме по собі не видаляє файл і не відкидає незбережену чернетку.

## W08 — Дерево файлів і контекстні дії

Готові іконки папок і зірочка головного файла праворуч.

- [ ] Обговорити меню, touch/keyboard доступ та маркер головного файла.
- [ ] Реалізувати й перевірити.

Прибрати меню «три крапки» активного файла над редактором. Перейменування, видалення, вибір головного файла та інші доречні дії перенести в контекстне меню відповідного елемента дерева. Правий клік працює для файла, який може не бути активним у редакторі. Для keyboard передбачити context-menu key/Shift+F10; для touch погодити доступну дію, не покладаючись лише на праву кнопку.

Додати іконки відкритих/закритих папок. Погодити компактний маркер головного файла замість тексту в кожному рядку: зірочка або інший символ із tooltip «Головний файл», без плутанини з дією «Обране». Вибір файла для редагування й головний файл залишаються різними поняттями.

## W09 — Створення та завантаження в обрану папку

Кнопка «Додати файл» відкриває меню створення та завантаження підтримуваних форматів.

- [ ] Обговорити одну точку додавання, назви дій і вибір директорії.
- [ ] Реалізувати й перевірити.

Замість двох різнорідних дій «Додати ресурс» і плюсика — попередня пропозиція однієї кнопки додавання з меню «Створити файл» / «Завантажити файл». Остаточні іконку й назви погодити.

Папку можна явно вибрати. Якщо вибрано папку, створення та завантаження спрямовуються в неї; якщо файл — пропозиція використовувати його батьківську папку; без вибору — корінь. За замовчуванням користувач вводить ім’я файла, а директорію бачить окремо й може змінити. Не вимагати щоразу вручну набирати повний шлях. Колізія назви не спричиняє мовчазного перезапису.

Поточне upload API приймає зображення, PDF і шрифти, а не текстові/Typst-файли. Погодити та реалізувати потрібну підтримку текстових файлів; новий напис «Завантажити файл» не має обіцяти непідтримувані формати.

## W10 — Операції над папками та drag-and-drop

- [ ] Обговорити модель папок, сценарії перетягування й конфлікти.
- [ ] Реалізувати й перевірити.

Додати доречні операції над папками: створення, перейменування/переміщення та видалення вмісту з підтвердженням. Погодити підтримку порожніх папок: зараз backend зберігає лише файли, а директорії виводяться з їхніх шляхів.

Розрізняти перетягування всередині дерева для переміщення файлів/папок і drop файлів з комп’ютера для завантаження в конкретну директорію. Показувати ціль drop і підсвічувати її; не дозволяти перемістити папку саму в себе чи її нащадка. Погодити підтримку drop цілих зовнішніх папок.

Переміщення папки змінює шляхи всіх її файлів атомарно. Зараз batch API має межу 200 операцій, а проєкт — до 500 файлів: для великих папок потрібне серверне рішення, не частково виконана серія запитів. Зберігати file ID, відкриті вкладки й чернетки. Окремо погодити поведінку `include`/`import` та відносних шляхів ресурсів після переміщення; автоматичного безпечного рефакторингу зараз немає.

## W11 — Resize панелей і локальне збереження розкладки

- [ ] Обговорити роздільники, межі розмірів і склад збереженого стану.
- [ ] Реалізувати й перевірити.

Додати перетягувані роздільники ширини дерева та співвідношення коду/PDF, а також висоти нижньої діагностики. Роздільники доступні з клавіатури; є мінімальні розміри, коректна поведінка при зміні viewport і повернення до стандартної розкладки.

Зберігати локально налаштування розкладки; серверна синхронізація зараз не потрібна. Погодити, що є загальним для акаунта, а що належить проєкту: ширини, режим, відкриті вкладки/порядок, активна вкладка, zoom/позиція PDF. Ізолювати стан за акаунтом і, де потрібно, проєктом. У localStorage не переносити тексти документів, контекст чи PDF. Недоступне сховище не блокує роботу.

Resize впроваджується після визначення основних панелей, щоб не реалізовувати його повторно для тимчасової розкладки.

## R01 — Дослідження швидкої компіляції та SmartTeX

- [ ] Знайти доступний код/опис SmartTeX і дослідити механізм.
- [ ] Виміряти поточний цикл і запропонувати варіанти.
- [ ] Окремо погодити реалізацію за результатами.

Це самостійне дослідження після базового W05; воно не блокує історію, вкладки та дерево. Порівняти звичайну компіляцію після автозбереження з інкрементальним або довготривалим ізольованим compiler session. Виміряти час від правки до PDF, окремо debounce/save, dispatch/polling, запуск sandbox, сам Typst, завантаження та рендер. Врахувати, що фонова PNG-обкладинка зараз також використовує compile worker: вона не повинна затримувати часті оновлення PDF або створювати зайву роботу.

Перевірити, чи SmartTeX справді використовує швидший шлях і який саме. Локального checkout SmartTeX у перевірених сусідніх проєктах не знайдено; механізм ще не встановлено. Згадку про винесення роботи з Docker не вважати фактом чи готовим рішенням. Не прибирати ізоляцію документів лише заради швидкості. SSE/WebSocket, якщо потрібні, лише доставляють оновлення; самі по собі не прискорюють компілятор.

Поточний compile API працює зі збереженими ревізіями. Компіляція незбереженої чернетки потребуватиме окремого контракту й рішення щодо того, коли результат стає прийнятим. Результат дослідження — вимірювання, варіанти з компромісами та окремий наступний обговорений крок.

## Як рухаємося

Основна черга: W01 → W02 → W03 → W04 → W05 → W06 → W07 → W08 → W09 → W10 → W11. R01 обговорюється окремо після появи базової автокомпіляції.

Для кожного пункту: спочатку погодити поведінку й вигляд; після доручення реалізувати frontend/backend разом, якщо потрібно; перевірити desktop/mobile, втрату даних, авторизацію та регресії відповідно до змін; оновити цей список і документацію. Комітити завершений блок після перевірок; дрібні рішення під час обговорення не комітити окремо.
