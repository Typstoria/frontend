# Правила інтерфейсу

Ці правила діють для всього проєкту: всіх екранів, компонентів, мокапів і майбутніх змін.

- Інтерфейс має містити лише елементи, потрібні для поточної дії користувача.
- Не додавати слогани, декоративні підзаголовки, рекламні описи, переліки переваг, повторення очевидного та ілюстрації без функціональної потреби.
- Не показувати технічні деталі реалізації, внутрішню конфігурацію чи недоступні інтеграції як постійні підписи. Якщо функція не налаштована, приховати її недоступну дію.
- У користувацьких повідомленнях не показувати request ID, trace ID, внутрішні коди помилок, HTTP-статуси чи stack traces. Ці дані залишаються в API та засобах діагностики; UI містить зрозуміле пояснення й потрібну дію.
- Кожен підпис має називати поле/дію, пояснювати необхідне обмеження або повідомляти про фактичний стан, помилку чи результат.
- Пояснення показувати в потрібному контексті й стисло. Не прибирати потрібні validation errors, попередження про втрату даних і повідомлення про результат операції.
- Не додавати перемикачі, мовні мітки чи інші контролі без реальної функції.
- Мокапи — візуальний орієнтир; ці правила й актуальні вимоги користувача мають пріоритет над декоративними елементами мокапів.

Під час UI-змін перевіряти вигляд і адаптивність на desktop та мобільному екрані.

# Зовнішні налаштування

Потрібні зміни в Google Cloud повідомляти користувачу окремо від локальних змін коду. Не вносити їх автоматично: користувач налаштовує Cloud сам або окремо доручає конкретну зміну.

# Координація агентів

У цьому проєкті використовувати субагентів за замовчуванням для змістовних задач реалізації, дослідження та рев’ю. Користувачу не потрібно щоразу окремо просити про делегування. Для коротких відповідей і тривіальних правок, де делегування не дає користі, головний агент працює сам.

Головний агент є координатором: уточнює вимоги, визначає архітектуру й контракти, розподіляє ділянки роботи, інтегрує та перевіряє результат. Складну логіку auth, ізоляції акаунтів, збереження, idempotency та конфліктів реалізує координатор або окремо доручений сильний агент.

| Роль                         | Модель / reasoning effort | Призначення                                                    |
| ---------------------------- | ------------------------- | -------------------------------------------------------------- |
| Координатор (головний агент) | `gpt-6.1-sol` / `high`    | План, складна реалізація, інтеграція й фінальна перевірка      |
| `explorer`                   | `gpt-6-luna` / `medium`   | Дослідження коду, API-контрактів і залежностей без змін файлів |
| `worker`                     | `gpt-6-luna` / `high`     | Обмежені задачі реалізації у визначених файлах                 |
| `reviewer`                   | `gpt-6.1-sol` / `high`    | Незалежне рев’ю суттєвих змін без редагування файлів           |

Моделі й інструкції ролей задано в `.codex/agents/*.toml`, типові налаштування — у `.codex/config.toml`. Явний вибір користувачем моделі чи режиму роботи має пріоритет над цими рекомендаціями.

- Перед делегуванням визначити мету, потрібний контекст, дозволені файли, узгоджені контракти, перевірки та очікуваний результат. Для вузьких завдань передавати стислий контекст, а не всю історію чату.
- Запускати незалежні задачі паралельно. Ліміт — до трьох одночасно відкритих субагентів, крім координатора; запускати лише стільки, скільки потрібно. Субагенти не створюють власних субагентів без окремого доручення координатора.
- На початку задачі доручати `explorer` обмежене дослідження, якщо є невизначеність у коді чи контрактах; чітко визначені невеликі зміни передавати `worker`. Перед завершенням суттєвих змін залучати `reviewer`, потім перевіряти та виправляти підтверджені знахідки.
- У спільному checkout одночасно редагувати різні файли. Координатор не редагує файли активного виконавця; спільні файли й API-контракти змінюються послідовно. Не відкидати чужі зміни, не комітити й не перемикати гілки з субагентів.
- Якщо інструмент запуску не підтримує вибір ролі, координатор передає інструкції відповідного TOML-файла та явно задає його модель і reasoning effort, якщо інструмент це дозволяє. Якщо потрібний режим недоступний, повідомити про обмеження; не видавати успадковану модель за налаштовану роль.
- Координатор відповідає за весь результат: читає зміни, запускає потрібні спільні перевірки й не покладається лише на звіт субагента. Не дублювати ті самі перевірки без нових змін або невизначеності. Не починати наступний блок продукту без доручення користувача.
